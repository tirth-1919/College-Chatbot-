# Phase 3A.4.4B — Step 3.1: Security Gap Closure

## Decision: READY FOR IMPLEMENTATION APPROVAL

This is a read-only investigation and design addendum to [Step 3](./phase3a4.4b-step3-final-approval-package.md). It resolves the five security questions with concrete implementation requirements. It does not claim that code, migrations, SQL, database behavior, or any test has been validated by execution.

The previously approved design decisions remain unchanged: 24-hour absolute visitor-token expiry; anonymous feedback requires the matching chat visitor token; guest support tickets are create-only; college chat analytics are aggregate-only; and the migration-history check determines in-place versus forward-only corrections. This addendum is controlling where Step 3 was less specific about worker identity, sensitive user-column access, signature replay, telemetry/audit writes, and SECURITY DEFINER ownership.

No `.env` file or secret value was read. No SQL, tests, migration, database connection, role, credential, key, container, or test data was created or changed.

## 1. Worker context

### Existing implementation and call sites

- [session.py](../../backend/app/database/session.py) signs context v1 with the web application's `RLS_CONTEXT_SECRET`. The signed fields are user ID, tenant ID, super-admin flag, email-verification flag, and expiry. `tenant_session()` accepts `college_id`, optional `user_id`, and `is_super_admin`; it has no worker purpose, job ID, resource ID, lease, or independent worker key.
- [document_tasks.py](../../backend/app/tasks/document_tasks.py) receives `document_id` and `college_id` in a Celery message, then calls `document_service.execute_document_processing()`. It checks that the document belongs to the supplied college, but that is only as trustworthy as the tenant context supplied to `tenant_session()`.
- [knowledge_tasks.py](../../backend/app/tasks/knowledge_tasks.py) receives `college_id` plus page IDs or a document ID. Its Celery and local-fallback paths both open unrestricted `tenant_session(college_id=...)`.
- [college_admin.py](../../backend/app/api/v1/college_admin.py) dispatches document work after resolving an authorized college; knowledge dispatch similarly receives a college ID and resource ID. These route checks are useful ingress controls, but the queue payload does not carry a database-validated job capability.
- FastAPI and task code use the same `async_engine` in [connection.py](../../backend/app/database/connection.py). The source does not establish a separate worker SQL principal or signing key. The code defines local async/background fallbacks; those execute in the web process and must not be treated as a separate worker trust domain.

### Gap

The database cannot distinguish a trusted worker from ordinary application code. A worker task trusts caller-supplied tenant/resource IDs, and any code holding the shared application signer can produce a valid context for an arbitrary tenant. The current HMAC prevents direct unsigned-GUC forgery; it does not prove that a signed `tenant_session(college_id=...)` was minted by a trusted dispatcher or authorized for a particular job.

### Exact proposed design

1. Add a dedicated `college_app_worker` database principal for the Celery deployment. It is `NOLOGIN` during migration/testing, then may receive a separately approved credential after security tests. It has `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS NOREPLICATION`, no membership/SET ROLE path to `college_app_user` or a privileged role, and only the job-claim and task-specific object/function grants. Do not share the web database URL or worker signing key with the API deployment.
2. Keep the approved web signer limited to non-worker purposes. Provision a separate worker signing key only to the Celery worker runtime via an approved secret manager. The web process must not load that key. The database key registry maps each `key_id` to an allowed purpose and verifier; a web key can never validate `WORKER`.
3. Add a `worker_jobs`/resource-lease record. It contains a generated job ID, allowed job kind, tenant ID derived from the validated resource, one or more exact resource IDs, state, lease expiry, and a hash of a random one-time lease token. Use one resource per job or a normalized child-resource table; do not accept an arbitrary tenant/resource list in the worker context.
4. An authenticated route validates the College Admin membership and resource ownership, then creates the job/transactional outbox entry. The Celery message contains only the generated job ID. It does not define the authoritative tenant or document/page IDs.
5. The worker claims a queued/expired job through a narrowly scoped `claim_worker_job(job_id)` function. It uses row locking, validates the job state and resource/tenant relationship, creates a five-minute lease, stores only the lease-token hash, and returns the authoritative tenant/resource IDs and the one-time token to the worker. A heartbeat every 60 seconds can renew the lease only for the same running job/token, up to the existing one-hour task hard limit; expired leases invalidate context immediately. The claim/heartbeat functions are executable only by `college_app_worker`.
6. For each database transaction, the worker signs a `WORKER` context containing the claimed job ID, tenant ID, exact resource IDs, lease-token digest, request ID, transaction ID, issue/expiry times, and key ID. The verifier checks the worker-key purpose, active lease, lease hash, non-expiry, and that each resource still belongs to the job tenant. Worker RLS policies authorize only rows reachable through that validated job/resource binding. A tenant GUC by itself grants no worker access.
7. Renew/reclaim leases through constrained functions. A stale, completed, cancelled, cross-tenant, or wrong-resource job fails closed. Celery broker ACL/TLS and publisher/consumer separation are required defense in depth; queue possession alone is not database authorization.
8. Local FastAPI fallbacks must not mint `WORKER`. Either run them with a validated initiating actor under `USER` context and only the same resource-scoped policies, or fail the job and report dispatch failure. They must not call a generic tenant setter with a caller-provided college ID.
9. Remove `is_super_admin` and arbitrary tenant selection from any generic worker-facing setter. Only the authenticated request dependency may establish `USER`; only a worker-only module with worker-only secret/DB principal may establish `WORKER`.

### Tests and migration impact

- Positive: authorized College Admin queues a document in A; a worker claims the resulting job and updates only that document; the job/tenant/resource binding survives task retry and lease renewal.
- Negative: API role cannot execute claim/worker functions or sign `WORKER`; forged task payload tenant/resource values are ignored; unknown, completed, expired, cancelled, or cross-tenant job IDs fail; a valid worker signature with a different document/page, tenant, lease token, or job ID is denied; raw GUCs and the API key cannot satisfy worker policies.
- Migration impact: create the worker role/job/lease objects and explicit role-specific policies before installing worker policies in the final context migration. Revise 017/019 interim policies and 021 final policies. Update document/crawler/knowledge task payloads and local fallback behavior. If any historical migration is deployed, implement additively in a reviewed forward migration, not by rewriting it.
- Human decision: approve the separate worker DB principal/key and choose actor-bound local fallback versus fail-closed queue-only behavior. Do not enable either login or secret until separately approved.

## 2. Sensitive user columns and ORM compatibility

### Existing implementation and actual query paths

The [User model](../../backend/app/models/user.py) maps: `id`, `email`, `hashed_password`, `full_name`, `role`, `is_verified`, `is_active`, `verification_token`, `reset_password_token`, `preferred_language`, `preferences`, `created_at`, and `updated_at`.

- [UserRepository](../../backend/app/repositories/user_repository.py) uses `select(User)` in both `get_by_id()` and `list_users()`. Those ORM entity queries select all mapped columns, including password/token fields. Its auth lookup uses the intended explicit seven-column function result.
- `get_by_id()` is called by [auth dependencies](../../backend/app/dependencies/auth.py), [auth_service.py](../../backend/app/services/auth_service.py), [users.py](../../backend/app/api/v1/users.py), [memberships.py](../../backend/app/api/v1/memberships.py), and [registration_repository.py](../../backend/app/repositories/registration_repository.py).
- [SuperAdminRepository.assign_college_admin()](../../backend/app/repositories/super_admin_repository.py) separately uses `select(User)` before changing `role`. Other user queries in the analytics service select only counts/IDs/role/active status; the college-admin directory selects only explicit display fields.
- The final function in [022_minimize_auth_lookup.sql](../../database/migrations/022_minimize_auth_lookup.sql) returns exactly `id`, `email`, `hashed_password`, `full_name`, `role`, `is_verified`, and `is_active`. The password hash is returned to the trusted backend for local password verification; it is not returned by `UserResponse` or the login response. Do not describe this as the hash never leaving the backend process.
- [UserResponse](../../backend/app/schemas/user.py) omits password and token fields. The development registration response in [auth.py](../../backend/app/api/v1/auth.py) intentionally returns the newly generated verification token only in development; preserve that behavior by returning the in-memory token once, not by granting SELECT on stored tokens.
- `verification_token` is used for email verification and is also reused by password-reset code in `AuthService`; `reset_password_token` and `last_login_at` have no backend read/write call site. `UserRepository.update()` flushes arbitrary ORM changes. Preference and profile changes, role/active changes, and password/verification changes therefore need distinct write boundaries.

### Gap and exact proposed privileges/functions

Leaving table-level `SELECT`/`UPDATE` grants in place defeats a sensitive-column allow-list. Revoking those grants without changing `select(User)` also breaks the ORM: its generated `SELECT users.*` will fail. Both sides must change together.

1. Revoke runtime table-level `SELECT`, `INSERT`, and `UPDATE` on `users`; retain no `DELETE`.
2. Grant column-level `SELECT` only for `id`, `email`, `full_name`, `role`, `is_verified`, `is_active`, `preferred_language`, `preferences`, and `created_at`, subject to RLS. Do not grant direct SELECT on `hashed_password`, `verification_token`, or `reset_password_token`; `last_login_at` and `updated_at` remain ungranted until an actual query requires them.
3. Keep `lookup_user_by_email_for_auth(text)` as the only password-hash read path. It returns the existing seven fields, is callable only by the backend SQL role, has an explicit non-login owner, and is not executable by PUBLIC. The app verifies the hash locally; it never serializes or logs it.
4. Replace generic `select(User)` calls with an explicit safe projection or `load_only()` for the columns in item 2. This applies to `get_by_id()`, `list_users()`, and `SuperAdminRepository.assign_college_admin()`. Use a safe account projection for read paths; do not later access a deferred sensitive attribute and trigger an implicit query. Keep count and directory projections as they are.
5. Replace generic user UPDATE/INSERT with narrowly scoped functions:
   - `register_student(...)`: insert only a generated ID, normalized email, password hash, name, fixed `STUDENT` role, active/unverified state, token hash/expiry, preferences/language, and timestamps. Do not accept a role or active-state parameter.
   - `update_own_profile(...)`: derive user ID from verified context; update only `full_name`, `preferred_language`, and `preferences`, and set `updated_at` in the database.
   - `update_user_admin(...)`: require verified Super Admin context; allow only the existing API's `full_name`, `role`, and `is_active` changes. Membership assignment calls this function rather than mutating `User.role` through a generic flush.
   - `issue_password_reset(...)`, `complete_password_reset(...)`, and `verify_email_and_consume(...)`: use separate, purpose-bound, expiring token hashes; compare/consume tokens and update password/verified state atomically. Do not return stored hashes/tokens or allow arbitrary updates. The current shared plaintext `verification_token` should not continue serving both purposes.
6. Use a high-entropy one-time token and store only its hash. Preserve public request/response semantics (generic reset-request response; development-only registration token returned once from memory); do not widen SQL read privileges. The existing forgot-password route currently discards the service's returned token rather than dispatching it, so end-to-end reset delivery remains a separate human/product decision and must not be silently invented in this phase.
7. Do not grant direct UPDATE on `updated_at` merely to make ORM `onupdate` work. The approved functions set it server-side. No table-level UPDATE may coexist with column-limited grants.
8. Adjust `prevent_user_privilege_self_change()` for the new function-only write paths. It must not retain a hard-coded exception for only `current_user = 'postgres'`; allow only the named, NOLOGIN definer owners used by verified invitation, credential, and admin-update functions, while rejecting changes made directly by `college_app_user`. No API role can `SET ROLE` to those owners.

### Tests and migration impact

- Positive: login reads the seven-field auth result and validates passwords; profile/preferences update; Super Admin can update user name/role/active state; email verification and password reset each consume only their own valid unexpired token; user list and `/me` retain existing response fields; development registration still returns its one-time in-memory token.
- Negative: `SELECT hashed_password`, either token column, or `last_login_at` through the runtime role fails; direct `SELECT *`, UPDATE, or DELETE on `users` fails; a safe ORM projection succeeds; profile context cannot change role/active/verified; non-Super Admin cannot call admin update; expired, wrong-purpose, reused token cannot mutate credentials; hashes/tokens never appear in JSON, logs, or audit payloads.
- Migration impact: adjust 018 grants; add/replace token hash/expiry fields and user functions in the final corrective migration; keep 022's seven-column return shape and give it an explicit restricted owner. Update `UserRepository`, `AuthService`, the user/membership administration routes, and response-focused tests.
- Human decision: approve the token purpose/expiry fields and reset-delivery behavior. No production reset token, credential, or `.env` data was examined.

## 3. HMAC replay protection, lifetime, and key handling

### Existing implementation and gap

[session.py](../../backend/app/database/session.py) sets transaction-local GUCs, signs context version 1, and sets expiry to current application time plus 300 seconds. [021_phase3a42_security_onboarding.sql](../../database/migrations/021_phase3a42_security_onboarding.sql) rejects expired timestamps and timestamps more than 300 seconds in the future. The verifier returns only a boolean; the key table is revoked from PUBLIC and `college_app_user`. The connection pool resets session state on check-in in [connection.py](../../backend/app/database/connection.py).

The signature has no issue-time field, request ID/nonce, key ID, or PostgreSQL transaction ID. Transaction-local GUCs are cleared at commit/rollback, but a captured valid signature can be replayed by setting the same signed values in a different transaction before its expiry. The key registry currently selects the single active key, so it has no defined overlap/rotation procedure.

### Exact proposed replay and rotation contract

1. Keep the maximum context-signature lifetime at **300 seconds**; this is a hard maximum, not a sliding session. Include `issued_at` and `expires_at`; the database verifies `issued_at <= now`, `expires_at > now`, and `expires_at - issued_at <= 300`. Reject excessive future issue time and every expired context. Use the database timestamp as the signing time to avoid app/database clock-skew ambiguity.
2. For every transaction, the backend first obtains `pg_current_xact_id()` and database time inside that transaction, generates a fresh cryptographically random UUID `request_id`, then signs the complete context. Sign and set, atomically: version, `key_id`, request ID, transaction ID, user, tenant, admin/email-verification flags, purpose, visitor-token digest, worker job/resource/lease claims when relevant, issue time, and expiry.
3. The verifier compares the signed transaction ID to `pg_current_xact_id()` for the current transaction. A context copied into another transaction fails even if the request ID/signature have not expired. A fresh request ID is generated for every transaction and is never accepted from HTTP input.
4. Replay policy: exact reuse of the same signed claims within the same transaction is permitted; it cannot change the actor, tenant, purpose, visitor capability, or worker resource. Cross-transaction replay is denied by transaction-ID binding. Each post-commit operation must obtain a new transaction ID and signature; never reuse an old signature after commit/rollback. Long jobs split database work into bounded transactions and re-sign at each boundary.
5. Add a signed key ID and purpose/issuer binding. The web key can sign only user/visitor/public-ticket contexts; the separate worker key can sign only worker contexts. Do not reuse the JWT signing key.
6. Keep verification keys only in the private database key table and the corresponding approved application secret store. The runtime roles have no schema/table access and no key-return function. The SECURITY DEFINER verifier reads the selected key internally and returns only a boolean or validated claims. Never log keys, signatures, bearer tokens, or raw context GUCs.
7. Rotation uses at least a two-key verification window: replace the current single-active-key constraint with separate per-key signing and verification-validity state, allowing one active signer per purpose while old and new verification keys overlap. Provision the new key under a new ID, deploy signers with the new key, accept the old key only until the maximum 300-second context lifetime plus a bounded rollout margin, then disable and remove it after confirming all signers have switched. The verifier accepts a key only for its configured purpose and validity interval. Rotation is documented and tested before production use; no key is provisioned in this phase.

### Tests and migration impact

- Positive: a valid context works within 300 seconds; a new transaction receives a new request ID/xid; overlap accepts old and new key IDs only during the approved rotation window.
- Negative: missing/malformed request ID, expired/overlong timestamps, altered signed field, wrong-purpose key, stale transaction ID, copied context in another transaction, and old key after retirement all return denied/NULL. Replaying a captured context in its original transaction grants no authority beyond its exact signed claims.
- Migration impact: update 021's key registry and verifier/helpers; update `set_rls_context()` and worker setter in `session.py`; update all context-setter call sites to re-sign after commits. Preserve the existing pool cleanup. For an already deployed chain, use a forward migration and coordinated signer rollout; never switch verifier format without an application/migration compatibility window.
- Human decision: confirm the 300-second maximum and secret-manager/rotation operator. Do not disclose or request key values.

## 4. Audit, AI telemetry, and notification logs

### Existing implementation and gaps

- `AuditLog` rows are directly constructed in [super_admin.py](../../backend/app/api/v1/super_admin.py) and [registration_repository.py](../../backend/app/repositories/registration_repository.py); `SuperAdminRepository.create_audit_log()` accepts an arbitrary ORM object. Current payloads include caller-supplied actor IDs and free-form JSON. The approval audit includes an admin email; the system-settings audit copies the request model; direct SQL INSERT can forge privileged events if the broad grants from 018 remain.
- [AIProviderService._log_telemetry()](../../backend/app/services/ai_provider_service.py) directly inserts `AIProviderEvent`. Actual event types include `GENERATION_SUCCESS`, `ALL_PROVIDERS_FAILED`, and `FALLBACK_FAILOVER`; the Super Admin connectivity probe inserts `SUCCESS`. The `error_message` field receives concatenated provider/model exceptions and fallback reasons, which can contain sensitive provider response/error text. There is no actor field or database-side actor check.
- [NotificationService.send_notification()](../../backend/app/services/notification_service.py) writes full recipient, subject, delivery content, error and metadata. The additional-information event stores the free-form `prompt` in metadata even though its `audit_content` is redacted. Rejection metadata can contain a free-form reason. Thus Step 3's redaction claim was incomplete for notification logs.

### Exact proposed write contracts

**Audit logs**

- Revoke direct runtime INSERT/UPDATE/DELETE. Keep SELECT for Super Admin through RLS.
- Add `record_admin_audit_event(action_type, target_entity, target_id, payload)` as the only runtime write path. It derives actor from a valid signed context; it accepts no `actor_user_id`, `college_id`, IP, user-agent, timestamp, or row ID from the caller. It requires a verified active Super Admin for the existing platform events and verifies persisted target/action pairings against current rows. For the existing in-memory `SYSTEM_SETTINGS_UPDATED` event, the function fixes the target name and generates the target ID itself rather than pretending a settings row exists.
- Initial allow-list from actual call sites: `COLLEGE_APPROVED` → `colleges`; `COLLEGE_ADMIN_ASSIGNED` → `college_memberships`; `AI_PROVIDER_CREATED` and `AI_PROVIDER_UPDATED` → `ai_provider_configs`; `SYSTEM_SETTINGS_UPDATED` → `system_settings`.
- Allow only event-specific payload keys: approval (`registration_id`, college name/slug only if approved; exclude admin email), assignment (`user_id`, role), provider create (`provider`, `model`), provider update (primary/active booleans), and settings (the six named operational fields). Reject unknown keys, secrets, token-like values, free-form prompt/message content, and oversized payloads. Actor and creation time are DB-derived.
- Direct writes from the five current call sites are converted to the function, in the same transaction as the state change. No caller can create a convincing audit row without passing the signed actor/target checks.

**AI provider telemetry**

- Revoke direct runtime INSERT/UPDATE/DELETE. Replace `error_message` with a fixed error category or omit it; never persist raw exception text, provider response bodies, prompts, messages, credentials, or request headers.
- Add `record_ai_provider_event(config_id, event_type, latency_ms, prompt_tokens, completion_tokens)`. `id` and `created_at` are DB-generated. `config_id` may be NULL for current generation calls that do not provide it; a non-NULL config must exist and be valid. `event_type` is restricted to the four observed values above. Metrics must be nonnegative and have explicit bounds. There are no text/JSON payload parameters.
- The function accepts no actor ID. It requires a currently valid signed USER or VISITOR context (or a validated WORKER job when the event is generated by a job); the connectivity probe requires Super Admin context and a valid config ID. Actor/tenant is validated from signed context, not a caller parameter. Keep aggregate reads Super-Admin-only.
- Convert both `_log_telemetry()` and the Super Admin probe to call the function. Error logging must use a stable category and redact exception/provider text; it must not log prompt or credentials.

**Notification logs (adjacent audit-data correction)**

- Revoke direct runtime table INSERT/UPDATE/DELETE; route writes through event-specific recorder functions. Derive event/college/recipient from a registration, invitation, or approved workflow row; validate the signed actor or the relevant public tracking/invitation capability.
- Permit only `REGISTRATION_SUBMITTED`, `ADDITIONAL_INFO_REQUESTED`, `REGISTRATION_APPROVED`, `REGISTRATION_REJECTED`, `COLLEGE_ADMIN_INVITATION`, and `ONBOARDING_COMPLETED`, plus transport-confirmed `SENT`/`FAILED`, DB-generated ID/time, and a redacted fixed summary. (`event_type` is currently varchar, not a database enum.) Do not persist the full email body, invitation URL/token, tracking code, arbitrary metadata, raw additional-information prompt, free-form rejection reason, SMTP/provider error text, or caller-selected recipient. For operational delivery, recipient may be retained only if approved as necessary PII and with a retention period; otherwise store a keyed/irreversible recipient reference.
- Update `notify_additional_info_requested()` to omit `metadata["prompt"]`; audit/notification text remains a short event summary. The transport status is supplied only after the transport result; timeout/failure maps to a fixed error category.

### Tests and migration impact

- Positive: each allow-listed action writes exactly one record with actor derived from signed context; approved provider events preserve current aggregate counts and token metrics; transport acceptance/failure produces the corresponding status.
- Negative: arbitrary actor/tenant/target, unknown event, action-target mismatch, unexpected JSON key, free-form prompt, secret-looking value, raw error, direct table INSERT/UPDATE/DELETE, anonymous/non-admin audit, and wrong-context telemetry are denied. Assert that rows contain no prompt, reply, token, credential, invitation URL, or raw provider error.
- Migration impact: update 017/019/021 RLS and 018 grants; add constrained functions and change ORM models/services/repositories. Preserve current successful aggregate analytics and notification outcomes, not arbitrary event-body persistence.
- Human decision: approve recipient PII retention/retention period for notification logs, fixed telemetry categories and metric bounds, and audit payload fields. Existing Step 3 approval of a `record_notification_delivery` function is retained but its former free-form prompt/metadata allowance is not.

## 5. College writes and every SECURITY DEFINER function

### Direct college writes and database enforcement

Current College ORM writes occur through `CollegeRepository.create/update()`, `SuperAdminRepository.approve_college/reject_college()`, and registration approval in `RegistrationRepository`; `/colleges` also has direct create/update routes. RLS policies alone cannot distinguish which columns the shared `college_app_user` is allowed to change. In particular, a row-level College Admin UPDATE policy does not stop that role from changing `status` or `is_active`.

**Recommended boundary:** direct runtime SELECT only on `colleges`; revoke runtime INSERT/UPDATE/DELETE. Route all writes through fixed, event-specific functions:

- Existing `submit_public_college_registration(jsonb)` is the public pending-registration path: it creates a `PENDING`, inactive college and its registration. `/colleges` creation must route to this flow for public applicants or be restricted to Super Admin; this preserves the Step 3 unresolved product decision and does not permit direct arbitrary tenant creation.
- `update_college_profile(...)` derives the actor and tenant from signed context, requires an active `ADMIN` membership for the target tenant (or verified Super Admin), and accepts only `name`, `official_domain`, `logo_url`, `contact_email`, and `contact_phone`.
- `decide_college_registration(...)`/`set_college_state(...)` requires verified Super Admin context, validates legal state transitions and registration linkage, and atomically changes `status`/`is_active` plus the associated review/audit record. No client can submit a forged actor ID or tenant.
- If direct approved Super Admin creation is retained, add a separate function that requires Super Admin context. Do not create a permissive generic insert/update function.
- Keep a trigger as defense in depth: reject changes to `status`/`is_active` unless the verified Super Admin/transition helper authorizes them. An HTTP dependency or generic column grant is not the database boundary.

### SECURITY DEFINER inventory and exact execution contract

The SECURITY DEFINER functions in 021 are currently created without explicit `ALTER FUNCTION ... OWNER`; their owner therefore depends on the migration executor. 022 explicitly preserves the existing owner for the auth lookup, which may be the privileged migration role. Search paths are fixed in the current definitions but often include `public`. The final design must assign explicit non-login owners and remove `public` from each `search_path`, fully qualifying all non-`pg_catalog` objects. No owner may be a login or have a membership path from runtime roles. Use distinct owners with only the table grants needed for their function group; do not leave these functions owned by an application or superuser login.
